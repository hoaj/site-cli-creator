## Pull requests

You have the maintainer's standing yes to merge: review and merge every PR you open in this repo yourself. This is the merge procedure; the `improve-site-cli-creator` skill points here.

1. **Wait for green:** wait for the PR's checks. When its changed files all fall outside the `paths:` filter of `.github/workflows/site-cli-creator.yml`, CI never runs and there is nothing to wait for. Check that against the filter, never from an empty `gh pr checks`.
2. **Review:** `/code-review high <n>`.
   - **Fixes:** in rounds one and two, fix every finding that holds up, with a red test first for a bug. The third round follows **The cap**.
   - **Another round:** when a round found a correctness problem, push the fixes and go back to step 1. When it found only cleanup, push, get green as in step 1 and go on to step 3.
   - **The cap:** three rounds at most. The third round's findings are not fixed in this PR. Check each one and drop those that don't hold up. What happens to the rest:
     - **Some hold the merge.** That is any finding that blocks a pipeline (CI, the five-platform matrix, release or install) or breaks something vital. Vital means, for example, an unwanted, unconsented or repeated write, lost or leaked data, a security hole, a broken Server sign-in or Session, or Starter code that breaks every generated CLI. When one of these is open, stop without merging, file nothing, and give the maintainer every open finding, including whether the five-platform matrix has run on that commit. A security hole is never a public issue (`SECURITY.md`).
     - **The rest don't.** Note them as follow-ups and carry on with the merge. They are filed in step 4, once the PR has merged.
       - **A fix that falls short.** A follow-up may show that the PR doesn't fully fix an issue it was meant to close. Note that issue as **fell short**. Before merging, remove every closing keyword for it (fix, close, resolve and their forms) from the PR body and title, and add `Part of #n` to the body. Something else can still close it on merge, such as a Development-sidebar link, which `gh` can't remove. Right before merging, note which fell-short issues `gh pr view <n> --json closingIssuesReferences` still lists. Step 4 undoes those closes.
3. **Merge.**
   - **Check main first:** `git fetch origin`. When `origin/main` has moved since the checks ran, merge it into the branch and push. A PR stacked on one that just squash-merged is different: merging main would conflict with the squashed copy of the base's commits. Rebase it instead:
     1. **Check the remote.** Note the branch's head `<h>` (`git rev-parse HEAD`). If `origin/<branch>` isn't `<h>`, someone else pushed to it. Stop and tell the maintainer instead of rebasing over their work.
     2. **Find your oldest commit.** `git log --reverse --oneline origin/main..HEAD` lists the oldest first: the base's commits, then yours. Your oldest commit is the first of yours in that list.
     3. **Rebase:** `git rebase --onto origin/main <your oldest commit>^`, then check that `git log --oneline origin/main..HEAD` shows all of your commits and none of the base's.
     4. **Push:** `git push --force-with-lease=<branch>:<h>`.
   - **After updating from main:** wait for green again. Review the update only if it needed conflicts resolved by hand; a clean merge or rebase needs no review. That review counts as a round. With rounds left, a correctness finding is fixed and sends the PR back to step 1, and cleanup is fixed in place. Once three rounds are used, its findings follow **The cap**.
   - **Five-platform matrix:** when the PR changes `install.sh`, `build.ts`, `main.ts`, `release.yml` or another Starter workflow, templating (`tools/lib/template.ts`), `package.json`, `bun.lock`, anything in the Starter CLI's `src/runtime/`, or its `tests/browser.test.ts`, `tests/transport.test.ts` or `tests/helpers.ts`, run `gh workflow run site-cli-creator.yml --ref <branch>`. Run it once, after the last review round and any merge of `main`, not after each round: it must be green on the PR's head commit. Its `test` job also runs a generated plugin's Chrome tests, on Linux only; the other targets run the smoke test. A runner or download failure before any test ran may be rerun once (`gh run rerun <id> --failed`). When it fails because of the PR and fewer than three review rounds are used, fix it, push and go back to step 1. On any other failure, stop without merging and tell the maintainer.
   - **Then:**
     1. `git fetch origin` again. When `origin/main` moved since **Check main first**, go back to it, and rerun the matrix if this PR needs one.
     2. Confirm `gh pr view <n> --json mergeable` says `MERGEABLE`.
     3. Note the PR's head (`git rev-parse HEAD` in the worktree). This is the commit the checks, review and matrix passed on. Then leave its worktree: ExitWorktree (keep), or `cd` to the main checkout when the session started inside it.
     4. From the main checkout, remove the worktree at the path `git worktree list` shows.
     5. Squash-merge: `gh pr merge <n> --squash --delete-branch --match-head-commit <head from 3> --body-file <file>` (no `--repo`, which would keep the local branch). The subject is the PR title (a repo setting). Write the body yourself, in a temp file outside the repo: a short summary and the PR's closing keywords, but none for an issue that fell short. Passing it explicitly keeps the branch commits' messages and trailers off `main`. `--match-head-commit` refuses a head that someone pushed after that.
     6. **Tag the version** the merge put on `main`, so `upgrade` can download its Starter code (SPEC §5). From the main checkout, in bash: `git fetch origin && .github/scripts/version-tags.sh origin/main | while read -r tag commit; do git push origin "${commit}:refs/tags/${tag}"; done`. It prints nothing when every version has its tag (a PR that did not bump). Your own `gh` login pushes it: GitHub refuses a tag on a commit with workflow files from Actions' token, which can't get the `workflow` scope that needs.
4. **File the follow-ups,** if **The cap** left any, after the merge:
   - **Fell short first.** This covers only the issues step 2 noted as **fell short**. GitHub closes the ones `closingIssuesReferences` still listed some time after the merge. Poll those together (`gh issue view <issue> --json state`) for up to five minutes. Reopen each as it shows CLOSED, and confirm it shows OPEN. Check them once more right before step 5, and report any still closed. Comment the finding on each fell-short issue instead of filing a new one.
   - **One issue per finding.** First search the open issues (`gh issue list --label site-cli-creator --state open --search <words>`) and comment on a match instead of filing a new one.
   - **Format:** a new issue gets `--label site-cli-creator` and the bug format of `skills/site-cli-creator-feedback/SKILL.md` (Intent, Where, Expected, Actual, Environment). The review's file, line and failure scenario go in Where and Actual, and the PR goes in Intent. Shapes, never values.
   - **The PR:** list the issues, including those that fell short, in its body under "Follow-ups (left open)", without a closing keyword.
5. **Tell the maintainer,** after the merge and once:
   - the PR, the version tag pushed in step 3, what the review found, the issues filed or commented on for findings left open, the issues that fell short (and any reopened), and the squash commit (`gh pr view <n> --json mergeCommit`). Issues that fell short are never counted as closed, here or in the Relay;
   - for a generator change, also the skill's Relay items (version, issues closed, cold-read result, Starter code reach).
