## Pull requests

You have the maintainer's standing yes to merge: review and merge every PR you open in this repo yourself. This is the merge procedure; the `improve-site-cli-creator` skill points here.

1. **Wait for green:** wait for the PR's checks. When its changed files all fall outside the `paths:` filter of `.github/workflows/site-cli-creator.yml`, CI never runs and there is nothing to wait for. Check that against the filter, never from an empty `gh pr checks`.
2. **Review:** one round, `/code-review medium <pr>`. There is no second round.
   - **Fixes:** fix every finding that holds up and fits this PR, with a red test first for a bug. Push, get green as in step 1 and go on to step 3. The fixes are not reviewed again.
   - **Left open:** a finding that holds up but is too large for this PR is not fixed here. Check each one and drop those that don't hold up. What happens to the rest:
     - **Some hold the merge.** That is any finding that blocks a pipeline (CI, the five-platform matrix, release or install) or breaks something vital. Vital means, for example, an unwanted, unconsented or repeated write, lost or leaked data, a security hole, a broken Server sign-in or Session, or Starter code that breaks every generated CLI. When one of these is open, stop without merging, file nothing, and give the maintainer every open finding, including whether the five-platform matrix has run on that commit. List the ones that don't hold the merge in the PR body under "Follow-ups (left open)", marking any that fell short (below), so whoever merges the PR later first handles those as **A fix that falls short** and then files the rest as in step 4. A security hole is never a public issue (`SECURITY.md`).
     - **The rest don't.** Note them as follow-ups and carry on with the merge. They are filed in step 4, once the PR has merged.
       - **A fix that falls short.** A follow-up may show that the PR doesn't fully fix an issue it was meant to close. Note that issue as **fell short**. Before merging, remove every closing keyword for it (fix, close, resolve and their forms) from the PR body and title, and add `Part of #<issue>` to the body. Something else can still close it on merge, such as a Development-sidebar link, which `gh` can't remove. Right before merging, note which fell-short issues `gh pr view <pr> --json closingIssuesReferences` still lists. Step 4 undoes those closes.
3. **Merge.**
   - **Check main first:** `git fetch origin`. When `origin/main` has moved since the checks ran, merge it into the branch and push. A PR stacked on one that just squash-merged is different: merging main would conflict with the squashed copy of the base's commits. Rebase it instead:
     1. **Check the remote.** Note the branch's head `<h>` (`git rev-parse HEAD`). If `origin/<branch>` isn't `<h>`, someone else pushed to it. Stop and tell the maintainer instead of rebasing over their work.
     2. **Find your oldest commit.** `git log --reverse --oneline origin/main..HEAD` lists the oldest first: the base's commits, then yours. Your oldest commit is the first of yours in that list.
     3. **Rebase:** `git rebase --onto origin/main <your oldest commit>^`, then check that `git log --oneline origin/main..HEAD` shows all of your commits and none of the base's.
     4. **Push:** `git push --force-with-lease=<branch>:<h>`.
   - **After updating from main:** wait for green again. Review the update only if it needed conflicts resolved by hand; a clean merge or rebase needs no review. That review (`/code-review medium <pr>`, of the hand-resolved conflicts only) follows step 2: fix what holds up, push and go back to step 1.
   - **Five-platform matrix:** when the PR changes `install.sh`, `build.ts`, `main.ts`, `release.yml` or another Starter workflow, templating (`tools/lib/template.ts`), `package.json`, `bun.lock`, anything in the Starter CLI's `src/runtime/`, or its `tests/browser.test.ts`, `tests/transport.test.ts` or `tests/helpers.ts`, run `gh workflow run site-cli-creator.yml --ref <branch>`. Run it once, after the review's fixes and any merge of `main`: it must be green on the PR's head commit. Its `test` job also runs a generated plugin's Chrome tests, on Linux only; the other targets run the smoke test. A runner or download failure before any test ran may be rerun once (`gh run rerun <id> --failed`). When it fails because of the PR, fix it, push and go back to step 1 (no new review). On any other failure, stop without merging and tell the maintainer.
   - **Then:**
     1. `git fetch origin` again. When `origin/main` moved since **Check main first**, go back to it, and rerun the matrix if this PR needs one.
     2. Confirm `gh pr view <pr> --json mergeable` says `MERGEABLE`.
     3. Note the PR's head (`git rev-parse HEAD` in the worktree). This is the commit the checks, review and matrix passed on. Then leave its worktree: ExitWorktree (keep), or `cd` to the main checkout when the session started inside it.
     4. From the main checkout, remove the worktree at the path `git worktree list` shows.
     5. Squash-merge: `gh pr merge <pr> --squash --delete-branch --match-head-commit <head from 3> --body-file <file>` (no `--repo`, which would keep the local branch). The subject is the PR title (a repo setting). Write the body yourself, in a temp file outside the repo: a short summary and the PR's closing keywords, but none for an issue that fell short. Passing it explicitly keeps the branch commits' messages and trailers off `main`. `--match-head-commit` refuses a head that someone pushed after that.
     6. **Tag the version** the merge put on `main`, so `upgrade` can download its Starter code (SPEC §5). From the main checkout: `bash -o pipefail -c 'git fetch origin && git show origin/main:.github/scripts/version-tags.sh | bash -s -- origin/main | while read -r tag commit; do git push origin "${commit}:refs/tags/${tag}" || exit 1; echo "tagged ${tag}"; done'`. It runs `main`'s own copy of the script, which compares with GitHub's tags, and prints nothing when every version has its tag (a PR that did not bump). `git push` uses git's credential, which needs the `workflow` scope: GitHub refuses a tag on a commit with workflow files without it, which is why Actions' token can't tag. Over HTTPS, `gh auth refresh -s workflow && gh auth setup-git` gives git your `gh` login. When the command fails or a push is refused, the merge stands: in step 4, file an issue labelled `site-cli-creator` that names the untagged version and the error, and report it in step 5.
4. **File the follow-ups,** if step 2 left any open or step 3.6's tagging failed, after the merge:
   - **Fell short first.** This covers only the issues step 2 noted as **fell short**. GitHub closes the ones `closingIssuesReferences` still listed some time after the merge. Poll those together (`gh issue view <issue> --json state,closedByPullRequestsReferences`) for up to five minutes. Reopen one that shows CLOSED only when this PR closed it (its number is in `closedByPullRequestsReferences`), and confirm it shows OPEN. One the maintainer or another PR closed stays closed: report it in step 5. Check them once more right before step 5, and report any still closed. Comment the finding on each fell-short issue instead of filing a new one. These findings are then done: they skip **One issue per finding** and **Format**.
   - **One issue per finding.** For every other follow-up, first search the open issues (`gh issue list --label site-cli-creator --state open --search <words>`) and comment on a match instead of filing a new one.
   - **Format:** a new issue gets `--label site-cli-creator` and the bug format of `skills/site-cli-creator-feedback/SKILL.md` (Intent, Where, Expected, Actual, Environment, Suggestion). The review's file, line and failure scenario go in Where and Actual, its proposed fix in Suggestion, and the PR in Intent. Shapes, never values.
   - **A failed tag:** always filed, whatever the review left, in the same format: the merged PR in Intent, step 3.6's command in Where, the version that should have been tagged in Expected, the error in Actual, and the git and `gh` versions in Environment.
   - **The PR:** list the issues, including those that fell short, in its body under "Follow-ups (left open)", without a closing keyword, replacing any findings step 2 listed there.
5. **Tell the maintainer,** after the merge and once:
   - the PR, the version tag pushed in step 3.6 (or that none was needed, or the error that stopped it), what the review found, the issues filed or commented on for findings left open, the issues that fell short (and any reopened), and the squash commit (`gh pr view <pr> --json mergeCommit`). Issues that fell short are never counted as closed, here or in the Relay;
   - for a generator change, also the skill's Relay items (version, issues closed, cold-read result, Starter code reach).
